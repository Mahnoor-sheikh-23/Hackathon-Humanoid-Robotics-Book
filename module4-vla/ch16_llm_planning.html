Chapter 16 - LLM-Driven Cognitive Planning for Robotics

Learning Objectives​

  • Understand the concept of cognitive planning in robotics using Large Language Models (LLMs).
  • Learn to decompose high-level goals into executable sub-tasks with LLMs.
  • Explore techniques for grounding LLM plans in robot capabilities and environmental context.
  • Implement a planning pipeline that translates natural language goals into a sequence of robot actions.
  • Analyze the benefits and challenges of LLM-driven planning in complex robotic tasks.

Introduction to LLM-Driven Cognitive Planning​

Traditional robot planning often relies on symbolic AI, state-space search, or optimization methods, which can struggle with ambiguity and open-ended tasks. Large Language Models (LLMs) offer a powerful new paradigm for cognitive planning, enabling robots to interpret abstract human goals, break them down into concrete steps, and reason about the world in a more human-like way. This chapter focuses on how to leverage LLMs to empower robots with advanced cognitive planning capabilities.

Core Concepts​

1. Cognitive Planning in Robotics​

  • Analogy: Cognitive planning is like a chess grandmaster mentally strategizing several moves ahead, considering all possible outcomes to achieve a winning position.
  • Plain English: This refers to a robot's ability to think, reason, and devise a sequence of actions to achieve a complex goal, often in an uncertain or dynamic environment. It involves understanding the goal, breaking it into smaller steps, and considering the consequences of each step.
  • Technical: Cognitive planning extends beyond traditional path planning to include high-level reasoning, decision-making, and symbolic manipulation. LLMs can facilitate this by generating logical sequences of actions, inferring missing steps, and adapting plans based on feedback or changing conditions.

2. Decomposing High-Level Goals with LLMs​

  • Analogy: Giving an LLM a high-level goal is like giving a project manager a broad objective; they then break it down into a detailed list of actionable tasks.
  • Plain English: LLMs can take a natural language goal (e.g., "make me a cup of coffee") and generate a step-by-step plan (e.g., "go to the kitchen," "get a mug," "brew coffee").
  • Technical: This involves prompting the LLM with the high-level goal and instructing it to output a sequence of sub-goals or actions. Effective prompt engineering guides the LLM to consider context, available tools/actions, and constraints. For example, the LLM might be asked to output a JSON list of actions, each with parameters, which can then be parsed and executed by the robot's lower-level control system.

3. Grounding LLM Plans in Robot Capabilities​

  • Analogy: Grounding an LLM plan is like making sure the project manager's tasks can actually be performed by the available team members and equipment.
  • Plain English: It's ensuring that the steps an LLM suggests are physically possible and make sense for the robot's specific abilities and the current environment.
  • Technical: Grounding involves mapping the abstract actions generated by the LLM to the robot's actual sensing and actuation primitives. This can be achieved through: a) Tool Use/Function Calling: LLMs are provided with a description of the robot's available functions (e.g., move(direction, distance), grasp(object)), and the LLM decides which function to call and with what arguments. b) State Representation: The robot's current state (e.g., location, grasped object, environmental map) is provided to the LLM as part of the prompt, allowing it to generate contextually relevant and executable plans.

4. Planning Pipeline Design​

  • Analogy: A planning pipeline is like an assembly line where each station performs a specific step: the first understands the order, the next designs the product, and the last builds it.
  • Plain English: This is the overall process where a human gives a command, the LLM creates a plan, and the robot then executes that plan, possibly with feedback loops.
  • Technical: A typical pipeline involves: 1) Goal Formulation: User provides a natural language goal. 2) LLM Planning: LLM generates a sequence of high-level actions. 3) Action Grounding: High-level actions are translated into low-level, executable robot commands (e.g., ROS 2 actions/topics). 4) Execution Monitoring: Robot executes actions, and sensors provide feedback. 5) Re-planning/Refinement: If an action fails or the environment changes, the LLM may be invoked again to re-plan or adjust.

Conceptual Hands-on Tutorial: Simple LLM Planning for a Virtual Robot​

Let's simulate an LLM-driven planning system. We'll use a Python script where a mock LLM (again, a rule-based system for simplicity, but easily replaceable with an actual LLM API call) breaks down a high-level goal into a sequence of simple robot commands. The "robot" will print its actions.

Step 2: Define Robot Actions (Tool Descriptions)​

In a real system, these would be descriptions provided to the LLM for function calling. For our mock LLM, we'll use them as internal logic. Create robot_actions.py:

# robot_actions.py
class RobotController:
    def __init__(self):
        self.current_location = "home"
        self.has_object = False
        print("Robot initialized at home.")

    def move_to(self, location: str):
        """Moves the robot to a specified location."""
        print(f"Executing: Moving to {location}")
        self.current_location = location
        return True

    def pick_up(self, obj: str, location: str):
        """Picks up an object at a specified location."""
        if self.current_location == location and not self.has_object:
            print(f"Executing: Picking up {obj} at {location}")
            self.has_object = True
            return True
        print(f"Failed to pick up {obj}. Robot is at {self.current_location}, not {location}, or already holding an object.")
        return False

    def place_down(self, obj: str, location: str):
        """Places down an object at a specified location."""
        if self.current_location == location and self.has_object:
            print(f"Executing: Placing down {obj} at {location}")
            self.has_object = False
            return True
        print(f"Failed to place down {obj}. Robot is at {self.current_location}, not {location}, or not holding an object.")
        return False

    def report_status(self):
        """Reports the robot's current status."""
        status = f"Robot is at {self.current_location}. Holding object: {self.has_object}"
        print(f"Status: {status}")
        return status

# Tool descriptions for LLM (example format)
ROBOT_TOOLS = [
    {
        "name": "move_to",
        "description": "Moves the robot to a specified location. Takes one argument: `location` (string).",
        "parameters": {"type": "object", "properties": {"location": {"type": "string"}}}
    },
    {
        "name": "pick_up",
        "description": "Picks up an object at a specified location. Takes two arguments: `obj` (string) and `location` (string).",
        "parameters": {"type": "object", "properties": {"obj": {"type": "string"}, "location": {"type": "string"}}}
    },
    {
        "name": "place_down",
        "description": "Places down an object at a specified location. Takes two arguments: `obj` (string) and `location` (string).",
        "parameters": {"type": "object", "properties": {"obj": {"type": "string"}, "location": {"type": "string"}}}
    },
    {
        "name": "report_status",
        "description": "Reports the robot's current status. No arguments.",
        "parameters": {"type": "object", "properties": {}}
    }
]

Step 3: Implement the LLM-Driven Planner​

Create llm_planner.py:

# llm_planner.py
import json
from robot_actions import RobotController, ROBOT_TOOLS
import os
from dotenv import load_dotenv

load_dotenv()

class LLMPlanner:
    def __init__(self):
        self.robot = RobotController()

    def mock_llm_plan(self, goal: str, current_state: str) -> list[dict]:
        """
        A mock LLM that generates a plan (sequence of tool calls) based on the goal.
        In a real system, this would be an API call to an actual LLM with tool use capabilities.
        """
        print(f"Mock LLM received goal: '{goal}' and state: '{current_state}'")
        plan = []

        goal_lower = goal.lower()

        if "get coffee from kitchen and bring to desk" in goal_lower:
            plan.append({"tool": "move_to", "parameters": {"location": "kitchen"}})
            plan.append({"tool": "pick_up", "parameters": {"obj": "coffee", "location": "kitchen"}})
            plan.append({"tool": "move_to", "parameters": {"location": "desk"}})
            plan.append({"tool": "place_down", "parameters": {"obj": "coffee", "location": "desk"}})
        elif "clean up the living room" in goal_lower:
            plan.append({"tool": "move_to", "parameters": {"location": "living_room"}})
            plan.append({"tool": "report_status", "parameters": {}})
            plan.append({"tool": "unknown_action", "parameters": {"task": "scan_and_identify_mess"}}) # Simulate a task LLM might suggest
            plan.append({"tool": "move_to", "parameters": {"location": "charging_station"}}) # Go charge after complex task
        elif "find my keys" in goal_lower:
            plan.append({"tool": "move_to", "parameters": {"location": "living_room"}})
            plan.append({"tool": "report_status", "parameters": {}})
            plan.append({"tool": "unknown_action", "parameters": {"task": "search_visual_keys"}})
        else:
            print(f"Mock LLM couldn't generate a specific plan for: {goal}")
            plan.append({"tool": "report_status", "parameters": {}})

        return plan

    def execute_plan(self, plan: list[dict]):
        """Executes a generated plan by calling robot controller methods."""
        for step in plan:
            tool_name = step["tool"]
            parameters = step["parameters"]
            print(f"\nExecuting step: {tool_name} with params {parameters}")

            # Dynamically call the robot controller method
            method = getattr(self.robot, tool_name, None)
            if method:
                success = method(**parameters)
                if not success:
                    print(f"Step '{tool_name}' failed. Re-planning might be needed.")
                    # In a real system, this would trigger a re-planning loop
                    return False # Stop execution on first failure for simplicity
            else:
                print(f"Error: Unknown tool/action '{tool_name}' in plan. Skipping.")
                # In a real system, LLM would be prompted to fix its plan
        return True

    def run_planning_cycle(self, goal: str):
        print(f"\n----- Starting Planning Cycle for Goal: '{goal}' -----")
        self.robot.report_status()

        current_state = self.robot.report_status() # Get current state for LLM context
        plan = self.mock_llm_plan(goal, current_state)

        if plan:
            print("\nGenerated Plan (from LLM mock):")
            for i, step in enumerate(plan):
                print(f"  {i+1}. {step['tool']}({', '.join([f'{k}={v}' for k, v in step['parameters'].items()])})")

            print("\n----- Executing Plan -----")
            self.execute_plan(plan)
        else:
            print("No plan generated. Cannot execute.")

        print("\n----- Planning Cycle Complete -----")
        self.robot.report_status()

if __name__ == "__main__":
    planner = LLMPlanner()

    # Example 1: Complex goal
    planner.run_planning_cycle("get coffee from kitchen and bring to desk")

    # Example 2: Another goal
    planner.run_planning_cycle("clean up the living room")

    # Example 3: Goal that current mock LLM can't fully plan
    planner.run_planning_cycle("find my keys")

    # Example 4: A simple goal to just report status (no complex planning)
    planner.run_planning_cycle("what is my status")

Step 4: Run the LLM Planner​

python llm_planner.py

Observe how the mock LLM decomposes the high-level goals into a sequence of simpler robot actions, and how the robot controller executes them. Pay attention to the unknown_action suggestions and error handling for failed steps, which simulate a real LLM's need for further prompting or re-planning.

Key Takeaways​

  • LLMs can serve as powerful cognitive planners, translating abstract human goals into concrete, actionable sequences for robots.
  • Prompt engineering is crucial for guiding LLMs to decompose goals effectively and output structured plans (e.g., JSON-formatted tool calls).
  • Grounding LLM plans involves mapping abstract actions to a robot's physical capabilities and providing current environmental context.
  • A planning pipeline integrates goal formulation, LLM planning, action grounding, execution, and potential re-planning.
  • Challenges include ensuring plans are executable, handling dynamic environments, recovering from failures, and managing the computational overhead of LLMs.

Exercises​

  1. Easy: Add a new simple goal to mock_llm_plan in llm_planner.py, for example, "go to the bedroom" and define a plan using move_to.
  2. Easy: Extend RobotController with a new action, light_on(room: str), and update ROBOT_TOOLS. Then, modify mock_llm_plan to use this action for a goal like "turn on the living room lights".
  3. Medium: Implement basic error handling in execute_plan that, upon a failed step, prints a message suggesting a re-planning attempt (without actually re-planning for now).
  4. Medium: Research how function calling or tool use features of actual LLMs (e.g., OpenAI, Anthropic) work. Describe how you would modify mock_llm_plan to use a real LLM API to generate the plan based on ROBOT_TOOLS.
  5. Medium: Enhance mock_llm_plan to incorporate the current_state more effectively. For instance, if the robot is already at the kitchen and the goal is "get coffee from kitchen", the LLM should not include move_to("kitchen").
  6. Hard: Design a mechanism for the LLMPlanner to monitor the execution of each step and, if a step fails, feed this failure back to the LLM (via a new replan method) along with the original goal and current state, asking it to generate a revised plan.
  7. Hard: Explore how a knowledge graph or semantic map of the environment could be integrated into the LLM's context to enable more intelligent and context-aware planning.
  8. Hard: Consider a scenario where the robot needs to interact with humans during a task (e.g., "ask user for help"). How would you incorporate human interaction as a "tool" in the LLM's planning process?
  9. Hard: Investigate hierarchical planning where an LLM generates a high-level plan, and then smaller, specialized LLMs or traditional planners refine individual steps. Describe the architecture.
  10. Hard: Discuss the challenges of real-time LLM planning for fast-moving or safety-critical robotic applications. What are potential mitigation strategies?
